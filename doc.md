# Backend — техническое описание реализации

## 1. Найденные проблемы

В ходе разработки и тестирования backend были выявлены следующие проблемы:

- **Риск overselling:** несколько параллельных запросов могли попытаться заказать один и тот же товар при недостаточном остатке.
- **Частичное создание заказа:** при ошибке во время создания заказа могли сохраняться не все связанные данные.
- **Повторное восстановление остатков:** повторная отмена заказа могла привести к многократному увеличению количества товара на складе.
- **Гонки при отмене заказа:** параллельные запросы на отмену одного заказа могли одновременно изменить его состояние и восстановить остатки.
- **Отсутствие валидации входных данных:** API и Store не проверяли часть некорректных значений.
- **Риск переполнения при расчёте стоимости:** умножение цены товара на количество и суммирование стоимости могли привести к переполнению `int64`.
- **Отсутствие ограничений на уровне БД:** некорректные данные могли попасть в PostgreSQL в обход прикладной логики.
- **Конфликты интеграционных тестов:** API- и Store-тесты использовали одну тестовую БД, из-за чего параллельная очистка таблиц приводила к нестабильным результатам и deadlock.

## 2. Способы исправления

### Создание заказа

- Используется транзакция PostgreSQL.
- Остаток товара уменьшается атомарным SQL-запросом с условием `stock >= quantity`.
- Для отсутствующего товара и недостаточного остатка предусмотрены разные ошибки.
- Создание заказа, добавление позиций и изменение остатков выполняются в рамках одной транзакции.
- При любой ошибке транзакция откатывается.

### Отмена заказа

- Отмена выполняется в транзакции.
- Перед изменением состояния заказа используется `SELECT ... FOR UPDATE`.
- Остатки возвращаются только при первом успешном переходе заказа в статус `cancelled`.
- Повторная отмена не приводит к повторному восстановлению остатков.

### Валидация

- Проверяются SKU, название товара, цена и количество на складе.
- Проверяются email покупателя и наличие позиций в заказе.
- Проверяются идентификаторы и количество товаров.
- Добавлена защита от переполнения при расчёте общей стоимости заказа.
- Дубликат SKU преобразуется в прикладную ошибку `ErrConflict`.

### Ограничения PostgreSQL

Добавлена миграция `002_constraints` с ограничениями:

- SKU и название товара не должны быть пустыми.
- Цена и остаток товара не могут быть отрицательными.
- Email заказа не должен быть пустым.
- Статус заказа должен соответствовать допустимым значениям.
- Общая стоимость заказа не может быть отрицательной.
- Название позиции заказа не должно быть пустым.
- Количество и цена позиции заказа не могут быть отрицательными или нулевыми соответственно.

### Интеграционные тесты

Добавлены тесты для Store и HTTP API:

- Успешное создание товара и заказа.
- Некорректные входные данные.
- Дублирование SKU.
- Отсутствие товара.
- Недостаточный остаток.
- Откат транзакции.
- Конкурентное создание заказов.
- Повторная и конкурентная отмена заказа.
- Проверка расчёта стоимости и переполнения.

## 3. Принятые архитектурные решения

- **Разделение API и бизнес-логики:** HTTP-обработчики отвечают за приём запросов, преобразование ошибок в HTTP-ответы и сериализацию JSON. Работа с данными сосредоточена в Store.
- **PostgreSQL как источник истины:** информация о товарах, заказах, позициях и остатках хранится в реляционной БД.
- **Транзакционный подход:** операции, затрагивающие несколько таблиц, выполняются атомарно.
- **Прикладные ошибки:** Store возвращает доменные ошибки (`ErrNotFound`, `ErrInsufficientStock`, `ErrInvalidInput`, `ErrConflict`), а API преобразует их в соответствующие HTTP-коды.
- **Дублирование критических проверок:** валидация выполняется на уровне приложения, а ограничения целостности дополнительно обеспечиваются PostgreSQL.
- **Миграции:** изменения схемы БД оформляются отдельными миграциями, а не изменением уже применённых миграций.

## 4. Особенности конкурентной работы

### Создание заказа

Уменьшение остатков выполняется атомарно:

```sql
UPDATE products
SET stock = stock - $1
WHERE id = $2
  AND stock >= $1
RETURNING name, price_cents;
```

Это позволяет PostgreSQL синхронизировать конкурентные изменения одной записи и не допускать продажи количества товара сверх доступного остатка.

### Отмена заказа

Для блокировки заказа используется:

```sql
SELECT id, status
FROM orders
WHERE id = $1
FOR UPDATE;
```

Блокировка строки заказа сериализует конкурентные операции отмены. Только один запрос может выполнить переход в `cancelled` и восстановить остатки.

### Проверка конкурентности

Реализованы тесты:

- `TestCreateOrderConcurrentStock`
- `TestCancelOrderConcurrent`

Конкурентная отмена дополнительно проверялась многократным запуском (`-count=50`).

### Изоляция тестовых БД

Для независимого выполнения тестов используются разные базы:

- `inventory_test` — Store.
- `inventory_api_test` — HTTP API.

Это позволяет пакетам тестироваться параллельно без взаимной очистки данных.

## 5. Известные ограничения

- Валидация email проверяет синтаксис адреса, но не подтверждает существование почтового ящика.
- Допустимые статусы заказа ограничены текущей моделью: `created` и `cancelled`. При добавлении новых состояний потребуется изменить миграцию.
- Защита от переполнения реализована для расчёта стоимости заказа. Переполнение при восстановлении остатков во время отмены заказа требует отдельной обработки.
- Проверки PostgreSQL не нормализуют значения SKU и названия автоматически. Нормализация пробелов выполняется на уровне Go.
- Тесты используют отдельные базы данных и требуют предварительно применённых миграций.
- Проверка `go test -race` подтверждает отсутствие обнаруженных гонок в тестируемом коде, но не гарантирует отсутствие всех возможных проблем конкурентного доступа в production.

## Результат

Реализована транзакционная работа с заказами, атомарное управление остатками, защита от повторной отмены, валидация данных на нескольких уровнях и интеграционные тесты для проверки корректности и конкурентного поведения.

Последняя проверка:

```bash
TEST_DATABASE_URL="postgres://postgres:postgres@localhost:5432/inventory_test?sslmode=disable" \
TEST_DATABASE_URL_API="postgres://postgres:postgres@localhost:5432/inventory_api_test?sslmode=disable" \
go test -race ./... -count=1
```

Результат: все тесты пройдены.
